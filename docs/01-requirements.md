# Requirements

**Status: DRAFT, under review.** Not final. Do not treat as approved scope until review is complete.

Priority: **MUST** (v1), **SHOULD** (v1 if time), **LATER** (after v1). Numbers are stable; new requirements fill gaps or use new groups.

## Catalog
- REQ-001 MUST: Each physical part has one canonical record identified by a unique **silverton_sku**, generated by the database (see REQ-090 to REQ-095).
- REQ-002 MUST: A part can have many aliases (manufacturer, supplier, OEM, legacy, barcode, customer).
- REQ-003 MUST: An alias is unique per (normalized number, source). The same number from different sources may map to different parts.
- REQ-004 MUST: Matching ignores case, spaces, dashes, and punctuation (`AB-1234` = `ab 1234`; a scanned silverton_sku matches with or without dashes).
- REQ-005 MUST: Aliases carry a `verified` flag; unverified matches are shown as such.
- REQ-006 MUST: Parts are never deleted; they are set to a status: active, hold, obsolete, or superseded.
- REQ-007 SHOULD: A superseded part points to its replacement.
- REQ-008 SHOULD: Admin can merge two parts; aliases, stock, fitment, and history move to the survivor and the merge is logged.
- REQ-009 SHOULD: Parts can have photos.

## Silverton SKU
- REQ-090 MUST: silverton_sku format is `CATEGORY-COLOR[-SIZE]-SUFFIX`, for example `HNG-BLK-M-7K4P`, or `HNG-BLK-7K4P` when the part has no size.
- REQ-091 MUST: The suffix is 4 random characters, unique across all parts, from digits 2-9 and letters excluding I, L, and O (31 characters, 0 and 1 also excluded).
- REQ-092 MUST: Category, color, size, and silverton_sku cannot change after creation. Mistakes are fixed by retiring the part and creating a new one.
- REQ-093 MUST: Size is optional; when absent, the size segment is omitted.
- REQ-094 MUST: Category (3-letter code), color (3-character code, mapped from the color name), and size (1-character code) are chosen from lookup tables with unique codes; users do not type them freehand.
- REQ-095 MUST: Parts without a meaningful color use the `NON` color entry.

## Locations
- REQ-010 MUST: Locations have a unique code and optional parent (warehouse > zone > shelf > bin).
- REQ-011 MUST: Each location has a scannable QR/barcode value.

## Stock and movements
- REQ-020 MUST: Every stock change is recorded as a movement; stock is never edited directly.
- REQ-021 MUST: Movement types: receive, move, issue, adjust.
- REQ-022 MUST: Stock at a location cannot go negative.
- REQ-023 MUST: Submitting the same idempotency key twice has no additional effect.
- REQ-024 MUST: Each movement records who, when, and an optional note.
- REQ-025 MUST: Show stock by part (with per-location breakdown) and by location.
- REQ-026 MUST: Show total on hand per part and flag parts at or below reorder point.
- REQ-027 MUST: Cycle count adjusts stock and requires a note.

## Scanning (phone)
- REQ-030 MUST: PWA runs on iPhone and Android and scans using the camera.
- REQ-031 MUST: Mode selector: Receive, Move, Issue, Count.
- REQ-032 MUST: Scanning any known alias or silverton_sku resolves to the canonical part.
- REQ-033 MUST: Unknown code prompts "link to existing part" or "create new part" (choose category, color, optional size; the SKU is generated).
- REQ-034 MUST: Quantity defaults to 1 with a quick numeric entry.
- REQ-035 MUST: Clear success/error feedback after each scan; ready for the next.
- REQ-036 SHOULD: Offline queue with later sync (safe via REQ-023).
- REQ-037 SHOULD: Works with Bluetooth/USB keyboard-style scanners.

## Purchasing
- REQ-040 MUST: Supplier parts hold supplier part number, cost, currency, lead time, MOQ, pack size, preferred flag.
- REQ-041 MUST: Creating a supplier part creates the matching alias automatically.
- REQ-042 LATER: Reorder suggestions from reorder point and lead time.

## Fitment (priorities to confirm)
- REQ-050 SHOULD: Record which products a part fits. Every product, including each variant, is its own independent record; there is no inheritance between products.
- REQ-051 SHOULD: Each fitment row can carry an optional assembly letter (1 or 2 characters) matching the product's assembly instructions. A letter is unique within a product.
- REQ-052 SHOULD: Fitment data may be incomplete. No row = fit unknown; row without letter = fits, letter not yet known. Parts are fully usable without any fitment.
- REQ-053 SHOULD: Admin can copy one product's fitment onto a product that has none, as a one-time copy.
- REQ-054 SHOULD: Look up which part is letter X in product Y, and which products use a part.

## Admin and reporting
- REQ-060 MUST: Admin screens for parts, aliases, categories, colors, sizes, locations, sources, suppliers, products, fitment.
- REQ-061 MUST: CSV import for parts, aliases, locations, fitment.
- REQ-062 SHOULD: Print location and part labels (silverton_sku as the barcode value).
- REQ-063 MUST: Movement history per part and per location.
- REQ-064 MUST: have an admin section to set up the warehouse location and bin structure.

## Security, audit, and quality
- REQ-070 MUST: Users sign in; movements are attributed to a user.
- REQ-071 LATER: Roles (scanner vs admin).
- REQ-072 MUST: Catalog records carry created_by, created_at, updated_by, updated_at, set by the database from the signed-in user. Movements carry created_by/created_at; stock carries updated_by/updated_at.
- REQ-073 MUST: Each user has a profile with a unique username, derived automatically from the email (text before `@`, lowercased, plus-tags removed) and editable afterward.
- REQ-074 MUST: Changes made without a signed-in user (imports, migrations) are attributed to a `system` profile.
- REQ-075 MUST: Users are deactivated, never deleted, so history stays attributed.
- REQ-080 MUST: HTTPS everywhere (required for camera access).
- REQ-081 MUST: Row-level security on all tables.
- REQ-082 MUST: Schema changes only via migrations.
- REQ-083 MUST: New tables are not auto-exposed to the Data API; every permission is an explicit grant in a migration.
